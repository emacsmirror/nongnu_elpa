Releasing VM

* NonGNU ELPA

Current package contents of GitLab vm/main will be at NonGNU-devel in
https://elpa.nongnu.org/nongnu-devel/vm.html.

You can test installing from here by add to package-archives:

(add-to-list 'package-archives 
             '("nongnu-devel" . "https://elpa.nongnu.org/nongnu-devel/"))

Note that it takes around 12 hours for an update to be available on
NonGNU-devel.

Once release is made with a release version number (1.2.3)
in vm.el, it will become available as a NonGNU ELPA
package at https://elpa.nongnu.org/nongnu/vm.html

* check for unexpected warnings
- make -j 32  # needs generated files
- make -j 32 lint

* check the committed reference appendix is current
- make -C info check-reference
It is generated from the docstrings but committed, because vm.texinfo
@includes it and makeinfo writes no manual at all without it -- and an ELPA
build never runs make.  See dev-guide.org.

* use package-lint to check vm.el packages
requires package-lint
  make package-lint
or 
  M-x package-lint-current-buffer
note lint will not be clean, due to xemacs references

* run the automated suite
- cd test && make test
- cd test && make test-leaks
- cd test && make test-imap   # needs a server in test/vm-live-config.el
- cd test && make test-assert

* run the mail-sending tests, if this machine can send mail
- cd test && make test-send

These send real mail and wait for it to arrive, which no other test does: the
rest stub `mail-send'.  They want a `vm-send-test-config' in
test/vm-live-config.el and skip without one, and they are deliberately not part
of `make test'.  They cover the first four items of the sending list below, so
what is left there for a person is the rest.

* manual testing

The suite reads no real mailbox and sends no real mail.  Every test stubs
`mail-send', so nothing automated has ever watched a message leave.  These
checks are the ones a person has to do, and they are the same every release.

Derive extra items from the NEWS.md section for the release: anything described
there as changed behaviour wants trying once by hand.

Sending.  `make test-send' covers the first four when configured; do them by
hand when it is not, and the rest either way:
- send to yourself with an Fcc header, and check the copy is filed, is in the
  folder's own format, and that the composition keeps its Fcc header
- a line past 998 characters, read back in something that is not VM
- a non-ASCII Subject, once with `vm-send-using-mime' nil and once with it on
- an Fcc naming an IMAP maildrop, against a real account
- an attachment, and a message with no body
- signed and encrypted, with vm-epg, and with an Fcc alongside
- reading what arrived in something that is not VM

Reading:
- an HTML part, internally and sent to an external viewer with pictures
- a message with a long recipient list, for shrunken headers
- a message whose headers arrive as raw 8-bit bytes

Folders, one of each type VM claims to read:
- From_, mboxcl2, mmdf, babyl; visit, save, expunge, and read the folder back
  with something that is not VM.  The folder type is written into the index
  file, so a type change is not only about parsing
- a folder reached through a symbolic link
- a Thunderbird folder, then opened in Thunderbird to see what it makes of it

Servers, against real accounts rather than the test dovecot:
- IMAP: get mail, save between folders, labels, expunge, disconnected mode
- Gmail, which is the awkward one: its IMAP does not keep keywords
- POP

Install, the whole way:
- package-vc-install from the fork, as below
- make distclean, autoconf, ./configure, make, make install, then run it

Anything found gets an issue of its own before the release goes out.

* tell the distribution packagers

Most distributions still ship 8.2.0b from 2011, because their automatic
new-version checks point at Launchpad, which VM left.  See issue #478 for what
each packager watches and how to correct it; until that is corrected they only
learn of a release by being told.

- Fedora: @goeran packages it and already builds from git.  Tell him the tag
  exists.
- Debian: reply on the open bug https://bugs.debian.org/1134674.  Debian is
  what Ubuntu, Devuan, Kali, Parrot, PureOS, Raspbian, Trisquel, Pardus and
  Deepin all rebuild, so it is the only one of these worth a conversation.
- Gentoo (gnu-emacs@gentoo.org), pkgsrc (pkgsrc-users@NetBSD.org), openSUSE
  (devel project =editors=, package =emacs-vm=): a version-bump bug each.
- Nix needs nothing.  It follows NonGNU ELPA.

Then check https://repology.org/project/emacs:vm/versions a couple of weeks
later.  It shows every distribution's version on one page, so it is both the
check that the release landed and the check that the watch-file corrections
took effect.
