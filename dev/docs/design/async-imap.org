* Async IMAP and POP Implementation Plan

All line references were verified against the tree at the time of writing.
Where a claim is not verified, it says so.

** Problem Statement

- VM blocks Emacs for the whole of every IMAP and POP network operation.
- The cause is synchronous accept-process-output in retry loops: the parser
  wants more bytes than the process buffer holds, so it waits for them.
- POP blocks the same way and is not a separate problem. It is the same
  problem in a smaller and simpler body of code.

** Where the blocking is

*** The primitive and its two wrappers

- vm-accept-process-output, lisp/vm-misc.el:91-97. Binds inhibit-quit to nil
  and calls accept-process-output. This is the only place VM waits.
- vm-imap-accept-process-output, lisp/vm-imap.el:473-489. The IMAP wrapper.
  Passes vm-imap-server-timeout, and distinguishes a timeout from a dropped
  connection by process-status.
- vm-pop-accept-process-output, lisp/vm-pop.el:766-782. The POP wrapper, and
  the same shape as the IMAP one: passes vm-pop-server-timeout, and tells a
  timeout from a dropped connection by process-status. All five POP reads go
  through it (lisp/vm-pop.el:800, 820, 849, 953, 1049).
- Until issue #639 POP had no wrapper and passed no timeout at any of the five
  reads, so vm-pop-server-timeout guarded only the connect (with-timeout at
  lisp/vm-pop.el:524) and a server that accepted a connection and then said
  nothing hung Emacs for ever.
- The wrappers differ in what they raise: IMAP signals
  vm-imap-protocol-error, POP a plain error (lisp/vm-pop.el:781, 782).

*** What the two protocols share, and what differs

Shared, and this is what makes one mechanism serve both:

- Both parse out of the process buffer, not out of the string the filter is
  handed. Both keep a buffer-local read point into it: vm-imap-read-point
  (lisp/vm-vars.el:7216, made local at lisp/vm-imap.el:1235) and
  vm-pop-read-point (lisp/vm-vars.el:7200, made local at lisp/vm-pop.el:513).
- Both waits have the same shape: a predicate over the process buffer is
  false, so wait for more input and test again. Nothing else is waited on.
- Both sessions are one command at a time with no pipelining, so there is at
  most one outstanding response per connection.
- Both open the connection the same way, both wrap it in with-timeout, both
  pause on auth failure with sleep-for 2.
- Both reach the primitive through a per-protocol wrapper that passes the
  protocol's server timeout and tells a timeout from a dropped connection by
  process-status (lisp/vm-imap.el:473, lisp/vm-pop.el:766).

Differs:

- POP terminators are found with a regexp search. The resume point is a
  buffer position and nothing else. A POP read can be re-run from scratch on
  the whole buffer and get the same answer, which makes it restartable.
- IMAP needs a parser because of {n} literals and nested lists.
  vm-imap-read-object is recursive, so its resume point is a stack of parser
  frames. A callback rewrite has to reify that stack; POP has no stack to
  reify. This asymmetry is the single largest difference in effort.
- An IMAP read failure signals vm-imap-protocol-error, which callers catch by
  condition; a POP read failure signals a plain error (lisp/vm-pop.el:781,
  782), which they can only tell apart by message text.
- IMAP tracks a session state machine (vm-imap-session-type, below); POP has
  no equivalent.

One mechanism can serve both, provided the primitive is stated as "resume when
this predicate over the process buffer becomes true" rather than as "resume
when a line arrives". The IMAP parser then supplies a predicate that means
"more input than last time", and POP supplies a regexp search. See the driver
in the section on keeping a blocking option.

*** unwind-protect cleanups an early return would break

- 58 unwind-protect forms in lisp/vm-imap.el, 7 in lisp/vm-pop.el.
- 20 condition-case forms in lisp/vm-imap.el, 7 in lisp/vm-pop.el.
- vm-imap-make-session, lisp/vm-imap.el:1224-1391. Cleanup pops the buffer-type

- vm-fetch-imap-messages, unwind-protect at lisp/vm-imap.el:3988, cleanup at

  timer, pops the stack and dumps uid/seq-num data. Its loop counts a local

  inhibit-read-only and buffer-undo-list t.

** Risk assessment

*** How much code a CPS rewrite touches

| item                                   | IMAP | POP |
| blocking read call sites               |   51 |  23 |
| send-command call sites paired to them |   32 |  19 |
| functions taking a process argument    |   40 |  11 |
| unwind-protect forms                   |   58 |   7 |
| condition-case forms                   |   20 |   7 |
| vm-*-make-session call sites           |   15 |   5 |
| interactive commands in the file       |   12 |   4 |
| of those, ones that use the network    |    8 |   2 |

- vm-imap-make-session call sites: lisp/vm-imap.el:612, 768, 879, 1006, 1396,
  2602, 2685, 4227, 4525, 4574, 4631, 4699, 4906, plus lisp/vm-reply.el:1087
  and lisp/vm-save.el:1037. 1396 is its own retry, so 14 distinct callers, 2 of
  them outside vm-imap.el.
- vm-pop-make-session call sites: lisp/vm-pop.el:148, 293, 372, 624, 1030. 624
  is its own retry, so 4 distinct callers, none outside vm-pop.el.
- Entry points from outside the two files: vm-imap-synchronize-folder at
  lisp/vm-folder.el:4243, 4897, 4902; vm-pop-synchronize-folder at
  lisp/vm-folder.el:4238, 4892; and the move-mail, check-mail, end-session,
  save-message, copy-message and append-message names used from vm-folder.el,
  vm-save.el and vm-reply.el.

*** What breaks loudly

- Nothing, by default. vm-assert is (or vm-assertion-checking-off ...),
  lisp/vm-macro.el:208, and vm-assertion-checking-off defaults to t,
  lisp/vm-vars.el:7289. All 48 buffer-type and session-type assertions in
  vm-imap.el are inert in a user's Emacs.
- They are live under ./test-runner --assert, so the test suite is where an
  interleaving bug would surface, and only if a test drives the interleaving.
- The design should not assume the assertions protect the field. Either turn
  them on for the async path, or accept that the class of bug they catch
  reaches users silently.

*** What breaks silently

- A misplaced read point. Nothing checks it beyond a vm-assert at
  lisp/vm-imap.el:1892. A continuation that resumes with vm-imap-read-point
  wrong parses the tail of one response as the head of the next and matches it
  against the wrong command.
- Response-to-command misattribution. vm-imap-send-command tags every command
  with the constant "VM" (lisp/vm-imap.el:1547, 1557); no call site passes a
  tag, and the three that pass nil pass no-tag t for continuation lines
  (1354, 3199, 4836). Matching is done on the literal symbol VM
  (vm-imap-read-response-and-verify, 2248-2255). So two commands in flight
  cannot be told apart by tag. Any design that allows more than one
  outstanding command must give commands distinct tags first, as a separate
  and testable change.
- A corrupted vm-buffer-types stack. It is a plain global; an unbalanced push
  produces no error, only a wrong answer from a later assert that is itself
  inert.
- vm-imap-session-type left at valid when an EXPUNGE has invalidated the
  sequence numbers. Sequence-numbered FETCH and STORE then address the wrong
  messages, which is the mechanism by which a flag lands on the wrong mail.

*** What could reach a user's mail

- Half-written folder. vm-imap-retrieve-messages inserts message text directly
  into the folder buffer (target is folder-buffer, lisp/vm-imap.el:3600) and
  only calls vm-assimilate-new-messages afterwards at 3632. Between those, the
  folder buffer holds bytes that belong to no message. Any suspension in that
  window exposes the folder to other commands.
- Rollback deleting the wrong text. The quit handler at lisp/vm-imap.el:3616
  deletes from old-eob to point-max. If anything else appended to the folder
  while the fetch was suspended, that rollback destroys it.
- Duplicated fetches. vm-fetch-imap-messages counts responses down against
  waiting (lisp/vm-imap.el:3995-4035) and leaves body-to-be-retrieved set on
  any message the server did not answer for, so it is asked for again. That is
  the right behaviour when a fetch is abandoned, but it means an abandoned
  continuation that already inserted a body without clearing the flag produces
  a second copy.
- Remote expunge. vm-imap-expunge-remote-messages, lisp/vm-imap.el:3662, sends
  EXPUNGE at 3729 driven by vm-imap-messages-to-expunge. That list is folder
  state, not session state, and an interleaved change to it between the STORE
  and the EXPUNGE deletes server mail that was not marked.
- POP deletes. vm-pop-move-mail issues DELE per message (lisp/vm-pop.el:224,
  256) and the server only commits them on QUIT. An abandoned session that
  never sends QUIT loses the deletes, which is the safe direction. A session
  that sends QUIT after a partial RETR loses the mail, which is not. Which of
  the two an interrupted async POP session produces depends on where the
  suspension lands; this needs a test before any claim is made about it.
  Since issue #639 the same interruption can be provoked synchronously, by a
  read timeout mid-session, so the test does not have to wait for the async
  rewrite.

*** What can be staged, and what is all-or-nothing

Safely staged, each independently useful and testable:

- Done, issue #639: POP reads go through vm-pop-accept-process-output
  (lisp/vm-pop.el:766) and pass vm-pop-server-timeout. It removed an unbounded
  hang and changed no control flow, which is the shape the rest of this list
  wants.
- De-duplicate lisp/vm-pop.el:1035-1071 against 837-875, so there is one POP
  UIDL wait loop rather than two.
- Give IMAP commands distinct tags instead of the constant "VM". Prerequisite
  for anything concurrent, and verifiable on its own against
  test/vm-imap-mock.el.
- Make vm-buffer-types per-session rather than global.
- Replace the sleep-for calls at lisp/vm-imap.el:939, 1314, 1359, 1373 and
  lisp/vm-pop.el:574, 596, 606. They are message pauses, not protocol, and
  they block Emacs for 2 seconds each for no protocol reason.
- Convert POP before IMAP: 23 call sites against 51, 6 frames against 11, no
  recursion, no session state machine.

All-or-nothing within one call chain:

- A synchronous caller cannot call an asynchronous callee. Converting
  vm-imap-read-object forces every one of the 51 read call sites and, above
  them, the 40 process-taking functions and their callers up to the
  interactive command. There is no partial conversion of a chain.
- The unwind-protect and condition-case forms in a converted chain all have to
  move at once: an error continuation cannot be introduced for some frames and
  not others, because a signal from a resumed frame does not reach a handler
  whose stack is gone.

** Can blocking remain an option?

Yes, and it should. But only in one direction: async underneath, synchronous
on top. The reverse is not available, because a blocking primitive cannot be
made to yield.

*** Option 1: two code paths, sync and async twins

- Every process-taking function gets a twin: 40 in IMAP, 11 in POP.
- Costs 51 plus 23 duplicated call sites, and every bug fix has to land twice.
- Rejected. The duplication is the whole file.

*** Option 2: one CPS path with a synchronous driver, recommended

- Write the protocol code once, in CPS. Provide two drivers over the same
  code.
- The synchronous driver starts the continuation chain and then pumps:

  #+begin_src elisp
  (defun vm-net-run-synchronously (thunk)
    "Run THUNK's continuation chain to completion, blocking as VM does now."
    (let ((state (vm-net-state-make)))
      (funcall thunk state)
      (while (not (vm-net-state-done state))
        (vm-accept-process-output (vm-net-state-process state)
                                  (vm-net-state-timeout state))
        (vm-net-state-poll state))
      (vm-net-state-value state)))
  #+end_src

- The timeout comes from the state, not from a constant: the two protocols
  have separate customs, vm-imap-server-timeout (lisp/vm-vars.el:815) and
  vm-pop-server-timeout (lisp/vm-vars.el:626), both nil by default. The state
  also decides which error a timeout raises, since the two wrappers do not
  raise the same one.
- The asynchronous driver installs a process filter that calls the same
  vm-net-state-poll and returns immediately.
- vm-net-state-poll is where the two protocols meet: it tests the pending
  predicate over the process buffer and, if it holds, resumes the
  continuation. IMAP supplies "the buffer grew"; POP supplies its regexp
  search. Nothing else differs between them at this layer.
- Cost: one path, plus a driver of about the size shown. The blocking option
  is then not a second implementation but a choice of driver, and it can be
  selected per command, per protocol or by a variable without any further
  duplication.
- A variable in the shape of vm-imap-connection-mode (lisp/vm-vars.el:822,
  read at lisp/vm-imap.el:3389, 3436, 3529, 3875, 3886, 3967, 3977) is the
  existing precedent for a mode that changes how the network layer behaves.
- What it does not buy: the code still has to be written in CPS, so all 74
  read call sites still change shape. The driver preserves the behaviour, not
  the source.

*** Option 3: generators

- generator.el ships with Emacs and VM requires 28.1, so iter-defun is
  available without a dependency.
- The attraction is at the leaves. vm-imap-read-object survives almost as
  written, with (iter-yield 'need-input) at the 4 places that now call
  vm-imap-accept-process-output, and its recursion becomes iter-yield-from
  rather than an explicit reified stack. That is the hardest part of the IMAP
  conversion, and generators are the only option that makes it cheap.
- The 51 call sites still change, but to iter-yield-from rather than to nested
  lambdas, which is a much smaller edit and leaves the code readable.
- An iter-defun cannot be called from an ordinary function, so the same
  explicit driver boundary as option 2 is needed, and the same two drivers sit
  on it.
- Unverified: whether generator.el's CPS transform copes with the whole of
  vm-imap-read-object, in particular unwind-protect inside an iter-defun. This
  needs a spike before the option is chosen.

*** Option 4: threads

- make-thread would leave every one of the 74 call sites as written.
- Emacs threads are cooperative under a global lock and yield at
  accept-process-output, so an IMAP thread would let the main thread run.
- Unverified and probably unsafe: almost all of vm-imap.el edits the folder
  buffer, and nothing in VM's data structures is protected against another
  thread editing them. The buffer-type stack alone is a global with 27 pushes
  and 34 pops. No claim is made here that this works; it needs an experiment,
  and the experiment should be regarded as likely to fail.

*** What the current shape makes easy, and what it makes hard

Easy:

- The waiting is funnelled. 4 sites in IMAP, all in one function; 5 in POP.
  Everything above blocks only by transitivity, so there is exactly one place
  per protocol to change the mechanism.
- Both parsers read from the process buffer, so the default filter behaviour
  of inserting at the process mark can stand. The filter only has to say "more
  arrived"; it does not have to hand the parser a string.
- One command outstanding per connection, so no correlation problem has to be
  solved before the first conversion.

Hard:

- vm-imap-read-object's recursion. A callback rewrite must reify a parser
  stack; a generator rewrite need not. This is the reason to take option 3
  seriously.
- 58 unwind-protect and 20 condition-case forms in vm-imap.el, each of which
  becomes an error continuation.
- vm-buffer-types is a non-re-entrant global, and
  vm-buffer-type:wait-for-imap-session already spins on it.
- Errors are signalled, not returned. vm-imap-protocol-error
  (lisp/vm-imap.el:454) and vm-imap-normal-error (459) both signal, and callers
  catch them with condition-case. In CPS the signal cannot reach the original
  caller's handler.
- The IMAP tag is the constant "VM", so concurrency needs a tagging change
  first.

** Prior art in this repository

The two mock servers are the design already working, on the server side.

- test/vm-imap-mock.el:531-566, vm-imap-mock--filter. Accumulates into the
  process property vm-imap-mock-pending, consumes whole lines, and switches to
  counting octets when an APPEND literal is pending
  (vm-imap-mock--take-literal). That is the same {n} literal problem the
  client parser has, solved in a filter, in about 35 lines.
- Its unwind-protect at 563-566 puts back whatever was not consumed, so an
  error costs one command and not the rest of the buffer. A client filter
  needs exactly this discipline.
- test/vm-pop-mock.el:242-266, vm-pop-mock--filter. Same shape, line at a
  time, same unwind-protect.
- Both use make-network-process with a :log function for accept
  (test/vm-imap-mock.el:629-633, test/vm-pop-mock.el:316-319).
- Both keep per-connection state in process properties rather than in a
  buffer, and detach and kill the buffer Emacs gives the connection
  (vm-imap-mock--connection-buffer-away). The client could do the same for
  everything except the parse buffer.
- Both still use sleep-for for the slow-greeting fault
  (test/vm-imap-mock.el:606, test/vm-pop-mock.el:290), which is fine in a test
  server and would not be in the client.
- The mocks also give the async work a test harness that needs no network:
  the fault injections (refuse, bad, drop-on, truncate-fetch, lie-about-size,
  slow-greeting, no-uidplus) are precisely the cases where a continuation is
  abandoned mid-flight.
- test/vm-pop-mock.el:126-129, the POP mock's silent-on fault: read a matching
  command and answer nothing. Added with issue #639, where it is aimed at STAT
  (test/vm-pop-mock-test.el:438); aimed at RETR or DELE it is the mid-session
  stall an abandoned continuation has to survive.

Event-driven code elsewhere in the tree:

- lisp/vm-grepmail.el:178-179 sets both a filter and a sentinel.
- lisp/vm-mime.el:4118-4121 and 4236-4239, filters and sentinels for external
  viewers; lisp/vm-save.el:804 and lisp/vm-crypto.el:144, sentinels.
- Timers already inside the protocol code: vm-imap-start-status-timer,
  lisp/vm-imap.el:179-184, run-with-timer 2 2; vm-pop-start-status-timer,
  lisp/vm-pop.el:717-722, run-with-timer 5 5; delayed delete-process at
  lisp/vm-imap.el:1508 and lisp/vm-pop.el:689.
- lisp/vm-folder.el:3905-3920 runs three repeating timers, one of them
  vm-auto-get-new-mail. So the blocking code is already re-entered from a
  timer, and vm-global-block-new-mail at lisp/vm-folder.el:4847 exists to stop
  it. Async does not introduce re-entrancy here; it removes the guard that
  currently makes re-entrancy rare.

** Recommended Solution: CPS with process filters

*** Why CPS

- No new dependency, on any supported Emacs.
- Incremental per chain, though not within a chain.
- The synchronous driver of option 2 keeps the old behaviour available.

*** Core pattern

**** Process filter replaces accept-process-output

#+begin_src elisp
(defun vm-imap-async-filter (process output)
  "Called when data arrives.  Never blocks."
  (let ((handler (process-get process 'response-handler)))
    (when handler
      (funcall handler output))))

(set-process-filter process #'vm-imap-async-filter)
#+end_src

The filter must still insert into the process buffer, because the parser and
the read point work there. It hands the parser a poll, not a string.

**** Commands take continuations

#+begin_src elisp
;; now, blocking:
(vm-imap-send-command process "LOGIN user pass")
(vm-imap-read-ok-response process)

;; after:
(vm-imap-send-command-async process "LOGIN user pass"
  (lambda (response)
    (if (vm-imap-ok-p response)
        (continue-with-select ...)
      (handle-error ...))))
#+end_src

**** Connection

Use make-process with :nowait t so the connect stops blocking too.

#+begin_src elisp
(make-process
 :name "imap-process"
 :buffer "*imap*"
 :host "imap.example.com"
 :service 993
 :filter #'vm-imap-async-filter
 :sentinel #'vm-imap-async-sentinel
 :nowait t)
#+end_src

**** Error handling

Every condition-case in the converted chain becomes an error continuation,
because the handler's frame is gone by the time the error occurs.

#+begin_src elisp
(vm-imap-login-async process user pass
  :on-success (lambda (result) ...)
  :on-error   (lambda (err) ...)
  :on-timeout (lambda () ...))
#+end_src

**** Timeouts

run-at-time replaces the timeout argument to accept-process-output; cancel it
when the response arrives. It has to reproduce what both wrappers do today:
give up after the protocol's server timeout, and report a dropped connection
as a dropped connection rather than as a timeout
(lisp/vm-imap.el:473-489, lisp/vm-pop.el:766-782).

** Alternative: aio.el

Cleanest source, at the cost of a dependency.

#+begin_src elisp
(aio-defun vm-imap-session (process user pass mailbox)
  (aio-await (vm-imap-login process user pass))
  (aio-await (vm-imap-select process mailbox))
  (aio-await (vm-imap-fetch-new process)))
#+end_src

Built on the same generators as option 3, so it buys syntax rather than
capability. https://github.com/skeeto/emacs-aio

** Migration path

1. The staged items above, each on its own: the duplicated POP UIDL loop,
   distinct IMAP tags, per-session vm-buffer-types, the sleep-for pauses. POP
   read timeouts are done (issue #639).
2. Spike generator.el against vm-imap-read-object, including unwind-protect
   inside iter-defun. Decide option 2 or option 3 on the result.
3. Build the state object and the two drivers. Cover them with the mock
   servers, using the fault injections for the abandoned-continuation cases.
4. Convert POP first: 23 call sites, 6 frames, no recursion. Ship it with the
   synchronous driver as the default so nothing changes for users.
5. Convert IMAP session setup, then vm-imap-select-mailbox, then the fetch
   path, each behind the same driver choice.
6. Switch the default driver to asynchronous only after the mock suite passes
   both ways.
7. Remove the synchronous driver only if it earns removal. Under option 2 it
   is small enough to keep indefinitely.

** Existing examples elsewhere

- nnimap.el in Gnus: sequence-numbered commands, still partly blocking.
- eimap: fully event-driven and streaming, but a complete rewrite.
  https://github.com/corecode/eimap

** Open questions

- Does generator.el's transform handle unwind-protect inside iter-defun well
  enough for vm-imap-read-object? Unverified, and it decides between option 2
  and option 3.
- What does an interrupted POP session do about pending DELEs? Whether an
  abandoned continuation reaches QUIT decides between losing deletes and
  losing mail. Needs a test against test/vm-pop-mock.el rather than an
  argument. The mock's silent-on fault aimed at RETR or DELE is one way to
  provoke it; not tried.
- Should the assertions be on for the async path? They are inert by default
  (lisp/vm-vars.el:7289) and they are the only check on the invariants an
  interleaving would break.
- Can vm-buffer-types be made per-session without disturbing the 95 sites that
  use the four buffer-type macros in vm-imap.el? Not investigated.
